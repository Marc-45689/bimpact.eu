BIM execution plan: 7 points to lock before modeling

2026-10-10 · 4 min read

BIM projects rarely go off track because of the software. They go off track because a question was left open at kickoff: who delivers what, when, in which format, and who checks it? The BIM execution plan exists to settle those questions before anyone starts modeling.

BIM requirements or BIM execution plan: who writes what?

The client writes the requirements, the project team answers with the execution plan.

The BIM requirements state what the client expects: what the model will be used for (CMMS, building management, asset register), which formats are accepted, which roles are expected. The BIM execution plan (BEP, called convention BIM or protocole BIM in France) describes how the project will actually be produced. It is written by the BIM manager, attached to the contracts and updated at every phase. It is both contractual and alive.

The 7 points to lock

1. Goals: why BIM on this project?

The answer changes how you model. A model for thermal analysis must be "watertight" and organized in volumes. A model for quantity take-off is organized by objects. Without a written goal, you produce data nobody will use.

2. Roles, and above all their scope

Naming the BIM manager is not enough. Do they only run the process and clash detection, or the schedule too? Does each party have a BIM coordinator responsible for its discipline model? Write it down. And state that the BIM manager facilitates the project: they are not its decision-maker.

3. Software and versions

An upgrade mid-project can break procedures that used to work. For each party, the plan fixes the software, version, native format and export format. Any update goes through the BIM manager.

4. Model organization

A single reference point, shared by every model, in absolute or relative coordinates. On a large project, a split into sub-models by trade, zone or level, so files stay workable. It sounds obvious. It is still the most common reason models fail to line up.

5. File and object naming

A file naming convention lets the federated model be assembled without ambiguity. A typical structure:

FieldExample
ProjectHBX
DisciplineELE (power), CFA (low voltage), HVAC, STR
OriginatorBMP
ZoneBATA
LevelR01
File typeM3D
VersionV03

Result: HBX_ELE_BMP_BATA_R01_M3D_V03. Same logic for objects, which can then be grouped into a single schedule even when they sit in several files.

6. Level of development per phase

For each object type, the geometry and information expected at each phase. I cover this in BIM LOD: what each level really requires.

7. Checks before each issue

They are defined before the first exchange, not after the first problem:

  • 3D check and consistency of the 2D drawings extracted from the model;
  • compliance with production procedures and schedule;
  • visual check (no duplicates, no stray objects) and check of filled-in parameters;
  • clash register, each clash assigned to the trade concerned, which remains responsible for the technical fix.

The plan also sets the exchange frequency, the platform and access rights.

My advice if you work as a subcontractor: ask for the execution plan before you price the job. If there is none, propose a short version covering at least points 3, 4 and 5. Those are the ones that block exchanges from the very first issue.

What about the legal side?

The plan should state who owns the models, who can access the data and where it is stored, what each party must do, including subcontractors, and who is liable if a third party modifies a model. Each producer of data remains responsible for the information they produce.

A short plan beats no plan

There is no need to aim for fifty pages. Ten pages that settle these seven points, signed by everyone, protect the project better than an exhaustive document nobody reads. The rest gets added phase by phase.
