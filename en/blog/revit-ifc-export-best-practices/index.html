IFC export from Revit: 6 best practices

2026-10-10 · 4 min read

Can the coordinator actually see your cable trays in the federated model? If the IFC export is not set up, they arrive as anonymous objects nobody can filter. IFC lets different software share one model. It still has to be configured.

IFC is an exchange format, not a working format

IFC (Industry Foundation Classes) is an open format, standardized as ISO 16739 and maintained by buildingSMART. It carries geometry, object properties and their relationships without depending on a vendor. It is the basis of openBIM.

It is not parametric, though. Revit's family, type and instance logic disappears on export: each element becomes fixed geometry with its properties. Everyone keeps working in their native format, and IFC is used only to exchange.

1. Use an up-to-date IFC exporter

Autodesk released the Revit IFC engine as open source in 2011. It evolves faster than Revit itself and offers a much richer export interface than the basic one. Install its latest release for your Revit version: many export defects are already fixed there.

2. Create one export setup per project

Do not start from the default settings. Duplicate a setup and save into it what the BIM execution plan requires:

  • the IFC version and the phase to export (IFC2x3 or IFC4, with the right model view definition);
  • splitting walls and columns by level, often expected by other software;
  • property sets: Revit properties, IFC common sets, base quantities;
  • storing the IFC GUID in Revit, so each object keeps the same identifier from one export to the next.

Then share the file with the whole team. Two exports made with different settings cannot be compared.

3. Get the class mapping table right

This is the setting that decides whether your objects are readable on the other side. Revit sorts objects by category, IFC by class, and the table links them: walls become IfcWall, doors IfcDoor. Without a mapping, Revit exports the object as IfcBuildingElementProxy, a catch-all class.

For electrical trades in IFC4, check at least these rows:

Revit categoryExpected IFC4 class
Cable traysIfcCableCarrierSegment
Cable tray fittingsIfcCableCarrierFitting
ConduitsIfcCableCarrierSegment (conduit)
Lighting fixturesIfcLightFixture
Electrical equipment (boards)IfcElectricDistributionBoard

The classic trap: generic models. Left unset, they all end up as proxies.

4. Force the class in the family

When a family fits no suitable Revit category, two shared text parameters set its class: IfcExportAs for the class, IfcExportType for the predefined type. Filled in the family, they override the mapping table. A well-built family is therefore designed for export from the start, template and parameters included.

5. Link a received IFC, do not open it

Opening an IFC in Revit creates a new project cut off from its source. When the sender updates their file, you cannot follow. A linked IFC reloads with each version, accepts snapping and dimensions, and is controlled view by view like any Revit link.

6. Check the IFC before sending it

An export is only validated once opened in an independent IFC viewer. Personally, I use BIMvision, which does the job very well. At minimum, check:

  • classes: no trade object as a proxy;
  • properties: the parameters required by the execution plan are present and filled in;
  • position: the model overlays the other trades at the right reference point;
  • colors: an object shown grey in Revit may appear white in the viewer, which hampers reading in meetings.

This check takes a few minutes. It saves you from finding out in a coordination meeting that your electrical networks are nowhere to be seen in the federated model.

The habit worth building

If you keep only one practice, keep the last one: open every IFC in a viewer before sending it. The export setup and the mapping table are set once per project. The check happens at every issue.
